# mali-open

An open Vulkan driver for Arm Mali GPUs on Android phones, written from scratch in C11. It runs in userspace on top of the vendor's
`mali_kbase` kernel driver, which exposes the GPU as a misc character device (`/dev/mali0`, 10:288) and not as a DRM device: there is
no render node, and every path that expects one is out of scope (see [Guest platform](#guest-platform-2026-11-20)). It needs no root and
no kernel changes. It is a Vulkan ICD (`libvulkan_mali.so`) for the Linux guest in which games run, targets Valhall-class CSF GPUs
(v10, v11, v13) and Vulkan 1.3.

**Status: pre-release (0.1.0).** It draws, computes, presents and passes part of dEQP-VK. It is not conformant, and the limits are listed below.

## Guest platform (2026-11-20)

What these kernels and guests do, checked on the Poco X8, the CMF and the Poco X4. Each row cost a session; none of them is a bug we can fix in this repo.

| Fact | Consequence for the driver |
|---|---|
| `/dev/mali0` is a kbase misc chardev (10,288 on one phone, 10,105 on another), with no sysfs uevent and no panfrost/panthor device behind it; major 226 is the display. (`vk/src/mali_physical_device.c:18-30`) | DRM/GBM/EGLDevice paths have nothing to open. The driver talks kbase ioctls plus dma-heap. |
| `/dev/dri` contains only the display `card0`. There is no render node on these kernels. (`vk/src/mali_physical_device.c:100-117` walks `/sys/class/drm` for exactly this reason) | `VK_EXT_physical_device_drm` can only answer `hasRender=false` (`:184-191`), and gamescope's renderer cannot start (see Limitations). |
| X11 needs DRI3 to hand a buffer to the server, and Xwayland here has none (`vk/src/mali_wsi.c:49-58,122-131`). | GLX/zink reports `dri3 extension not supported`; GL clients create no Vulkan swapchain at all; X11 present falls back to shm/PutImage: correct, but slow. |
| Proot `--link2symlink` plus a uutils multicall binary breaks `#!/usr/bin/env`: the kernel execs the stubbed `.l2s.env…`, uutils' name check aborts, the session dies in ~20 ms with `GUEST_EXIT 1`. | Guest scripts must use `#!/usr/bin/python3`. Fixed upstream in DroidDeck #2930 (`fix/guest-python-shebang`, `d5f5b9c17`); not in this tree. |
| `/dev` is tmpfs on these phones. | Nodes vanish on reboot; the guest launcher binds `/dev/mali0` at session start by its *current* minor (DroidDeck `LinuxRuntime.java:345-390`). Never hardcode a minor in a launch script. |

## Why

Mali phones usually have no usable system Vulkan driver for desktop-style workloads. The alternative is a bridge, which forwards calls to
Android and adds round trips and copies. A driver that talks to kbase directly can use async submit, cached memory, zero-copy
presentation and the extensions DXVK and vkd3d-proton need. The aim is plug-and-play for Mali users through MediaDeck: import a zip, select the driver.

## Architecture

1. `libkbase/` is the lower layer. It has no Mesa dependency and uses the kbase ioctls, memory (BOs), contexts, CSF queues, tiler heap, fences and fault decoding.
   It is selected through a per-GPU version table.
2. `vk/` is the Vulkan front end (`vk/src/mali_*.c`): instance, device, memory, buffers, images, descriptors, pipelines, command
   buffers, meta operations, queries, events, WSI.
3. `mali_backend.h` separates the front end from the kernel. There are two backends: `kbase` (real) and `fake` (offline tests).
4. Per-arch code (v11, v13) is compiled twice. Differences are `#if PAN_ARCH >= 13` sites.
5. The shader compiler is not ours. Mesa 26.3.0 is linked as a library, unmodified: `spirv_to_nir`, NIR, the Bifrost/Valhall backend
   and the `vk_*` runtime and WSI. Our own NIR passes sit in `mali_compile.c` and `mali_descriptor_lower.c`.
6. Mesa's Panfrost texture, format and blend helpers are linked too (`pan_format`, `pan_texture`, `pan_blend` and similar).
7. PanVK is an oracle only. We run it for comparison, and no file from `src/panfrost/vulkan` is copied. `check.sh` asserts that no `panvk` symbol is exported.
8. The libkbase uAPI header is written by us from public documentation and observed behaviour. No Arm DDK source and no blob disassembly are used.
9. Binary 1.3 device (`api_version 1.3`), with features advertised only when a test backs them.
10. The build reads compile flags and the library list from a pinned Mesa build tree (`vk/build.sh`).

```

vk/cross/build-cross.sh all      # aarch64 glibc and bionic cross builds

```

`MALI_BACKEND=fake MALI_FAKE_GPU=v11|v13` runs everything that does not touch hardware (loader, caps, compile, descriptors, command-stream bytes versus golden).
`docs/host-harness.md` lists exactly what the desktop can and cannot prove before a phone run (and why a passing host gate never removes one hardware smoke run).
Hardware runs use two small harnesses on a rooted-free phone: a direct run (a bionic test binary that loads the ICD without a loader and issues
Vulkan calls: `t_icd --direct`, `t_vk_draw`, `t_vk_feat`, ...) and a guest run (the glibc build through the Khronos loader, plus dEQP-VK via `vk/deqp/qdeqp.py`).
The phone-side scripts are the maintainer's lab; the automatic test farm that drives them is in this tree (`tools/farm/GUIDE.md`, `tools/farm/README.md`).
The Mesa sources, Mesa build trees and the CTS are not committed: `third_party/MESA-SOURCE.txt` pins the Mesa tag and commit.

## Running it in a guest

The guest's Vulkan loader picks the ICD (`VK_ICD_FILENAMES`/`VK_DRIVER_FILES`, or whatever json the session already selects).
`MALI_WSI_DEBUG=1` prints what the driver chose; without it most failures are silent.

**Check the sha before you deploy.** Lanes deploy exactly one artefact, `vk/out/a64-glibc-wsi/libvulkan_mali.so`, built by
`tools/build-artefact.sh` (`--check` reprints an existing one); it prints `path + sha256 + commit` and refuses a dirty tree. Deploy
only when that sha256 is the one the lane's branch head produced — a stale `vk/out/` survived a branch switch once and every "new"
WSI run silently loaded the old driver, with no memory budget in it.

**Discover the ICD, do not assume a path.** The stock library and its sha differ per rootfs (one guest keeps its own under
`/usr/local/lib/mali-open/`, another has only `/usr/lib/aarch64-linux-gnu/libvulkan_panfrost.so` and points the json at it), so find it
(`find /usr -name 'libvulkan_*.so'`, `vulkaninfo --summary`) and back up the exact file you replace. A deploy is only proven by
`driverName mali-own` in `vulkaninfo --summary`; the json name and an app's driver picker can both lie.

**The trap:** if the session's `VK_ICD_FILENAMES` is `/usr/local/share/vkbridge/droidbridge_icd.json`, our driver is not loaded at
all — the MaliBridge ships its own ICD shim, forwards to the host GPU, and the session can look perfect (`Mali-G925-Immortalis MC11`,
Arm proprietary `v1.r49p1`, 158 extensions) while `libvulkan_mali.so` sits idle. `BL_VKBRIDGE=0` in the session env is ignored; the
switch is the app's `vkBridge` pref (DroidDeck `SessionPrefs.kt:1021`), and it reverted `false → true` by itself before a run, so re-read it
immediately before any driver-mode measurement.

| Variable | Effect |
|---|---|
| `MALI_WSI_DEBUG=1` | one line per swapchain creation (platform, format, present mode, extent, DRI3/Present/MIT-SHM, result) and the DRM node decision (`vk/src/mali_wsi.c:152,273`, `vk/src/mali_physical_device.c:181-193`) |
| `MALI_VRAM_CAP_MB` | overrides the device-wide commit budget `min(heap/2, RAM/4)` (`vk/src/mali_physical_device.c:422-436`) |
| `MALI_BO_POOL_MB` | BO pool size, 64 MiB per device by default; `0` really disables it, frees go back to `MEM_FREE` (`vk/src/mali_backend_kbase.c:24,147`, `t_bopool`) |
| `MALI_DRM_PRIMARY`, `MALI_DRM_RENDER` | node for `VK_EXT_physical_device_drm`, as a path or `maj:min`; `DD_DRM_*` and `VKBRIDGE_*` aliases are accepted (`vk/src/mali_physical_device.c:142-144`) |
| `MALI_WSI=dmabuf` or `MALI_WSI=sw` | force a present path (tests only); `MALI_WSI_FORCE_NO_DRI3=1` makes the client behave as if the server has no DRI3 |

## Measuring

- Displayed fps only: SurfaceFlinger present timestamps or the on-screen HUD. Producer-side `render_fps`, `presented_fps` and uncapped rates are different quantities and are never reported as fps.
- 3 reps of 30 s, median, and every point keeps its rep count and `panel_hz`.
- Clear the diagnostic env first (`VKBRIDGE_STATS`, `VKBRIDGE_FRAME_TRACE`, `MALIDECK_KEEP_DIAG`). It cost 15.5 fps (90.9 with, 106.4 without, same device and mode), so any number taken with it is ~15 % low.
- A sample with `fps > panel_hz + 2` is an instrument error: reject it, do not clamp it.
- `profile=uncapped` is not comparable with `default` and never sets a best.

## Shipping in MediaDeck

`vk/package/build-zip.sh` builds an importable zip (`libvulkan_panfrost.so` is our library under the name the importer accepts,
plus `meta.json`, `icd.json`, `LICENSE`, `NOTICE-MESA.txt`). Variants: `a64-glibc`, `a64-glibc-wsi` (Wayland + X11 WSI, the shipping one), `a64-glibc-wl` (Wayland only). `--bundle` also writes a
driver-pair zip. `verify-zip.sh` checks a zip. Import and selection steps: `vk/package/README.md`. Note: on a phone that has a vkBridge, the app uses the bridge and ignores the imported driver.

## Limitations

- gamescope cannot work in driver mode: `drmGetDeviceFromDevId()` resolves a node through sysfs, so a bind-mounted `/dev/dri` node can never satisfy it and both of gamescope's backends refuse without one. Returning `hasRender=false` is the honest answer, not a bug to work around (`vk/src/mali_physical_device.c:184-191`, `9476179`).
- X11 present has three paths (`vk/src/mali_wsi.c`), chosen by the probe *before* the swapchain exists, never as runtime
  recovery after a failed import: dma-buf with DRI3+Present (default when the server has both), our own
  MIT-SHM segment (a SysV segment plus `XShmPutImage`, `mali_x11_shm_create`), and plain `XPutImage` as the last resort.
  The SHM segment needs neither DRI3 nor `EXT_external_memory_host` — it is the default for an X server without DRI3, and
  `MALI_WSI=dmabuf`/`MALI_WSI=sw` still force either path. Without any of them GL presents slowly.
- Wayland present is proven on hardware: `vkcube --c 20` on the X8, 20/20 presents, exit 0, 45.8 fps median. X11 present is
  proven on the host harness only (`vk/tests/xwsi-host.sh`); there is no device run of the X11 software path yet, and the
  Steam windows appearing is not evidence that their scene paints. The fake backend issues no kbase BO flags, so the
  dma-buf shareability fix (`COHERENT_LOCAL` on imports, `libkbase/src/bo.c`) is proven by the device run alone, not by
  `vk/check.sh`.
- Performance is not uniform (see the generated table above, which is the source of truth): on the Poco X8 (G925) every row is at or above the bridge, on the CMF (G615) the cubes are at 74-89 % and triangle-3k above the bridge. The Poco X4 (G610, v10) has no `ours` cube row; its triangle row is 44 % of the bridge.
- Draw-count scaling (CMF, `bench/README.md`): 5k, 10k and 20k draws per frame now work, but at 10k/20k our CPU ms per frame is above the bridge's. No poco-x8 5k/10k/20k rows have been published yet.
- Known dEQP fails: `a2r10g10b10` `sample_count_4` fails on v11 and v13 (baseline refreshed, not fixed), plus the 27 sample failures below. `logicOp`, `vertex_attribute_divisor` and part of the Steam/zink gap list are still open (`vk/STEAM-GAPS.md`).

- Not conformant: dEQP numbers above are a sample, 27 sample cases fail on the v13 run. The committed `vk/deqp/ours-daily-sample-*.tsv` baselines are older (301-302 pass) and are refreshed by `farm bless`.
- v13 coverage is thinner than v11. A geometry-buffer size regression broke v13 draws and was fixed, so recheck draws on every change.
- MSAA is experimental and off by default (`MALI_EXPERIMENTAL_MSAA=1`; the 4x `a2r10g10b10` case still flakes), no geometry or tessellation shaders, no GPL, no robustness2 bounds clamping.
- Firmware support is a fixed list (uAPI 1.21 and 1.30). Other versions are refused on purpose.
- Games were not yet run end to end through DXVK. That is the R4 gate.
- The licence of the project itself is not yet decided: see `LICENSE-NOTES.md`.

## Unverified or next

- **gamescope in driver mode**: a dead end as things stand (see Limitations). Unblocking it is kernel work or the bridge, not this ICD. Do not spend another session on the layer or on `MALI_WSI` variants.
- **Steam UI on the software present path**: it renders only software-composited at ~7 fps; GPU-composited CEF is impossible here (X11 needs DRI3, `libcef.so` has no `vkCreateWaylandSurfaceKHR`, Wayland ozone fails to connect). Untested past that.
- **kbase descriptor layout warning**: `layout UNVERIFIED, expect faults` is emitted when the packer's descriptor generation does not match the arch from `gpu_id` (`libkbase/src/draw.c:37-43`, `libkbase/src/ctx.c:118-121`). It cannot mis-size an allocation, but it is unfixed and it is shown on v13.
- **Buffer-bound memory**: the budget is a guard, not a fix. kbase still commits and pins every page at allocation time (`libkbase/src/bo.c:45`); commit-on-demand is not implemented.
- **v10 (Poco X4)**: no cube row, and no DroidDeck app installed there at the moment (MIUI blocks adb installs), so v10 is the biggest data gap.
- **Steam-menu fps**: the remaining regression is the older bridge inside the stock app (72.0/69.4/70.7 → median 70.7 on the X8 at 120 Hz), not the driver or the panel. Unconfirmed on a second phone.
